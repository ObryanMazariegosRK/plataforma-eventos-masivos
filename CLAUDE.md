# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Mass ticket-sales platform ("Plataforma de Eventos Masivos", Análisis de Sistemas II, UMG). Modular monolith on Laravel 13 / PHP 8.4 / MySQL 8 / Redis, run entirely in Docker. Code, identifiers, comments and commit messages are in **Spanish** — keep that convention.

## Commands

Everything runs inside the `app` container (host PHP is not assumed):

```bash
docker compose up -d --build                     # start stack (first time: --build)
docker compose exec app composer install
docker compose exec app php artisan migrate      # or migrate:fresh while schema is in flux
docker compose exec app php artisan test         # all tests
docker compose exec app php artisan test --filter=NombreDelTest   # single test/method
docker compose exec app php artisan test tests/Unit/AlgoTest.php  # single file
docker compose exec app ./vendor/bin/pint        # code style (Laravel Pint)
docker compose logs -f queue                     # queue worker output
docker compose restart queue                     # REQUIRED after changing code used by jobs/queued mail (the worker keeps old code in memory)
docker compose exec app php artisan reservas:demo-concurrencia   # live concurrency demo against MySQL (parallel HTTP reservas; creates and deletes its own event/users; --conservar keeps them)
docker compose exec app php artisan bitacora:instalar     # once per machine (and after pulling new database/migrations/bitacora): creates the eventos_bitacora DB, its SELECT/INSERT-only user and tables
```

If you get HTTP 500 on a fresh clone: `docker compose exec app chmod -R 777 storage bootstrap/cache`.

Services: app http://localhost:8090, Adminer http://localhost:8082, Mailpit http://localhost:8026, MySQL on host port 3308 (user `eventos` / `root`, db `eventos`). Inside the Docker network, hosts are `mysql` and `redis`.

Tests use SQLite in-memory, `QUEUE_CONNECTION=sync` and array cache/session (see `phpunit.xml`), so they do not need the MySQL/Redis containers — but MySQL-specific migration features must stay SQLite-compatible for tests to pass.

## Architecture

Clean architecture, sliced per module. Each layer has one folder per module (`Admin, Auth, Boletos, Catalogo, ColaVirtual, Inventario, Notificaciones, Pagos, Pasarelas, Recintos, Reembolsos, Reservas, Transacciones`), scaffolded by `scripts/create-modules.sh` (empty dirs hold `.gitkeep`):

- `app/Domain/Entities/<Modulo>/` — plain PHP entities (no Eloquent). Constructor-promoted private props, a private `validar()` called from the constructor that throws `DomainException`, behaviour methods that enforce state transitions (e.g. `Reserva::confirmar()`, `cancelar()`, `vencer()`), and explicit getters. `Reserva` is the reference example.
- `app/Domain/Enums/<Modulo>/` — string-backed enums for states/types (`EstadoReserva`, `EstadoAsiento`, …); values match what's stored in DB `estado` columns.
- `app/Domain/Abstractions/<Modulo>/` — repository interfaces (`I<Entidad>Repository`) and service interfaces (e.g. `IPasswordHasher`, `ITokenService`, `IEnviadorCorreoAuth`).
- `app/Domain/Exceptions/<Modulo>/` — business exceptions extending `ReglaDeNegocioException` (itself a `DomainException`). The domain knows nothing about HTTP: the exception → `[status, error code]` map lives in `bootstrap/app.php` (`withExceptions`). Any other `DomainException` (e.g. from an entity's `validar()`) renders as 422. **Controllers never use try/catch** — throw, and register new exceptions in that map.
- `app/Application/Abstractions/<Modulo>/` — use-case interfaces (`I<Accion>UseCase`, single `execute()` method). Controllers depend on these interfaces, never on concrete use cases.
- `app/Application/UseCases/<Modulo>/` — use-case implementations (`<Accion>UseCase`).
- `app/Application/DTOs/<Modulo>/` — readonly input DTOs.
- `app/Data/<Modulo>/` — **all repository implementations go here** (`<Entidad>Repository`, mapping Entity↔Model). This is the only layer, besides `Models`, that touches Eloquent. The folders are created per module as repositories are added.
- `app/Infrastructure/<Modulo>/` — implementations of service interfaces backed by the framework or third parties (hashing, Sanctum tokens, mail/Mailables, payment gateway adapters). **Never put repositories here.**
- `app/Models/<Modulo>/` — Eloquent models (persistence only).
- `app/Http/Controllers|Requests/<Modulo>/` — HTTP layer.

Bind every interface to its implementation in `AppServiceProvider::register()` — both the repository (`Domain/Abstractions` → `Data`) and the use case (`Application/Abstractions` → `Application/UseCases`). Read settings via `config()` (e.g. `config/reservas.php`, `config/autenticacion.php`), never `env()` outside `config/`. Use cases don't call `config()` either: the controller reads it and passes the value in the DTO (e.g. `ttlSegundos`, `minutosValidezCodigo`), so use cases stay unit-testable with plain PHPUnit and in-memory fakes (`tests/Fakes/<Modulo>/`).

Note: the README's architecture tree is slightly out of date (it shows use cases directly under `Application/<Modulo>/`); the actual folders are as listed above.

Most modules are still skeletons: domain entities/enums and migrations exist, but most use cases, repositories, models and controllers are unimplemented. Complete vertical slices: `POST /api/reservas` (`CrearReservaUseCase`; behind `auth:sanctum`, the user id comes from `$request->user()`, never from the request body; receives `evento_id` + `inventario_ids` of `disponible` seats, locks them and computes the total from `precios`; `ExpirarReservasVencidasUseCase` runs every minute and frees seats of expired reservas) and the Auth module under `/api/auth/*`. Scheduled tasks are declared in `routes/console.php` (e.g. `sanctum:prune-expired` daily). API routes live in `routes/api.php` (registered in `bootstrap/app.php`, prefixed `/api`, JSON exceptions).

### Authentication

Laravel Sanctum bearer tokens. The authenticatable model is `App\Models\Auth\Usuario` (table `usuarios`, set in `config/auth.php`). Flow: `registro` (always creates `cliente`, emails a 6-digit code — see Mailpit) → `verificar-correo` (returns a token) → `login` (rejects wrong credentials 401, blocked 403, unverified 403) → `logout`/`perfil` behind `auth:sanctum`. Password recovery: `olvide-password` (separate `codigo_recuperacion`) → `restablecer-password` (revokes all tokens). Codes are destroyed after `Usuario::MAX_INTENTOS_CODIGO` failed attempts, and the code endpoints are throttled. `VerificarUsuarioActivo` is appended to the whole `api` middleware group, so a `bloqueado` user is rejected (403) on every request even with a still-valid token. Logged-in users can `cambiar-password` (requires the current password; keeps the current token, revokes the rest) and `logout-todos`. Password rules live in `Password::defaults()` (`AppServiceProvider::boot`). Auth mailables implement `ShouldQueue`: they go to Redis and the `queue` container sends them — in tests assert with `Mail::assertQueued`, not `assertSent`. No admin UI yet: promote/block users with SQL (see `http/README.md`). Google login (Laravel Socialite) uses WEB routes `/auth/google/redirect` → `/auth/google/callback` (`GoogleAuthController`; Socialite stays in the controller, the use case `IniciarSesionConGoogleUseCase` receives a DTO). It finds by `google_id`, else links by email (wiping the password of an unverified local account to prevent pre-hijacking), else creates a verified `cliente` with null password. The token is handed to the browser in the URL fragment (`/oauth/google#token=...`). Errors in the callback are turned into a redirect to `/login?tipo=error&mensaje=...` by a render callback in `bootstrap/app.php`. Requires `GOOGLE_CLIENT_ID/SECRET/REDIRECT_URI` in `.env`; tests mock `Socialite::driver->user`. Role guard: `->middleware(['auth:sanctum', 'rol:admin,organizador'])` (`App\Http\Middleware\VerificarRol`). Error responses are `{"message", "error"}` where `error` is a stable code for the frontend.

### Payments (Pagos / Pasarelas)

Two-step flow like real gateways (the frontend's `Auth.irAPagar(reservaId)` in `autenticacion.js` starts it right after reserving and from the retry links, skipping the `/pagar` chooser when exactly one gateway is active; the gateway page shows a countdown to the reserva's expiry): `POST /api/pagos` (`IniciarPagoUseCase`: PENDIENTE pago, amount always from the reserva, gateway order → `url_aprobacion`) → the browser approves on the gateway page → `/pagos/retorno?pago=ID` calls `POST /api/pagos/{id}/confirmar` (`ConfirmarPagoUseCase`). Confirm runs in ONE transaction (`IUnidadDeTrabajo`, single attempt — never auto-retry a charge) with pago and reserva locked: reserva confirmed, inventario items sold, then the **capture is the last step**; a rejected capture throws `PagoRechazadoException` (402), rolls back, and a second transaction marks the pago `rechazado`. Confirm is idempotent. Gateways implement `Domain/Abstractions/Pasarelas/IPasarelaPago` and are picked by code in `Infrastructure/Pasarelas/PasarelaPagoResolver` (only `simulada` today: orders in cache, fake gateway page at `/pasarela-simulada/{orden}` where the buyer types a test card from `config('pagos.simulada.tarjetas')`: `aprobada` 4242 4242 4242 4242 is shown there to copy, `sin_fondos` 4000 0000 0000 9995 tests a rejected payment, both 12/30 CVV 123; anything else stays on the page as "datos incorrectos" and leaves the order pending. `IPasarelaPago::crearOrden()` receives `venceEn` = the reserva's `expira_en`, so a gateway order dies with its reserva (`pagos.simulada.minutos_orden` is only an upper cap); it is kept in cache one more day, so revisiting the gateway URL (browser Back, bfcache reload) shows `pasarelas/simulada-estado` — already processed / rejected → link to `url_retorno`, expired → back to the catalog, unknown → 404 — and re-posting the form never processes twice; seed with `PasarelaSeeder`). Cross-module effects go through ports implemented as adapters: `IRegistroVenta` → Transacciones (VENTA + historial `VENTA_CONFIRMADA`, inside the transaction) and `IProcesadorPostVenta` → `ProcesarCompraConfirmadaJob` (afterCommit: Boletos' `IEmitirBoletosUseCase`, then `NotificarCompraConfirmadaUseCase`). Confirm refuses (409 `reserva_no_pagable`, no charge) a reserva without `inventario` rows, since Boletos emits one ticket per seat.

### Refunds (Reembolsos)

Policy in `config/reembolsos.php` (`tramos`): ≥ 7 days before the show → 100 %, ≥ 72 h → 80 %, ≥ 24 h → 50 %, < 24 h → no refund (`CalcularReembolsoUseCase`); if the show was postponed (`eventos.reprogramado_en`, set when a published event's date changes) it is 100 % until it starts (`por_reprogramacion`). The customer always gets back what the policy says of what they paid: the gateway keeps its commission, Soirée absorbs it. One request per payment. Client: Mis compras shows "Solicitar reembolso" on upcoming purchases → dialog fed by `GET /api/reservas/{id}/reembolso` (`ConsultarReembolsoDeCompraUseCase`: amount today, policy table, or `motivo_no`) → `POST` same URL `{motivo?}` (`SolicitarReembolsoDeCompraUseCase` → Freyder's `SolicitarReembolsoUseCase`, state `solicitado`); each purchase in `GET /api/mis-compras` carries `reembolso {estado, monto, fecha}` (several refunds of one purchase are summarized: the least advanced state wins) and `evento_cancelado`. Admin panel section "Reembolsos" (`public/js/admin-reembolsos.js`, admin only): `GET /api/admin/reembolsos?estado&periodo&pagina` (`ListarReembolsosAdminUseCase`, pending first, `por_estado` counts; `periodo` = `hoy|semana|mes|anio` by request date in Guatemala days, from `config('reembolsos.periodos')`; 10 per page + "Ver más"). Resolve with `PATCH /api/reembolsos/{id}/resolver {decision}`: **approving** annuls the purchase's `emitido` tickets and puts its seats back on sale (`inventario` → `disponible`, `reserva_id` null; not when the event is cancelled) in the same transaction, then `ProcesarReembolsoUseCase` refunds through the gateway (`IPasarelaPago::reembolsar(referenciaCobro, monto, claveIdempotencia)` — key `reembolso-{id}`, so a retry never pays twice), marks it `procesado` and records a `REEMBOLSO` transaction + historial `REEMBOLSO_CONFIRMADO`; if the gateway fails it stays `aprobado` (`devolucion_pendiente: true`) and `POST /api/admin/reembolsos/{id}/procesar` retries (409 `reembolso_no_procesado` while it keeps failing). **Rejecting** keeps the tickets. The client gets a queued email when the refund is `procesado` or `rechazado` (`NotificarResolucionReembolsoUseCase`). Cancelling an event (`POST /api/eventos/{id}/cancelar`) approves and refunds 100 % automatically. The reserva stays `confirmada`; a refunded purchase still lists its seats through its annulled tickets (`boletos.inventario_id`), and since a released seat can be sold again, `boletos` is unique per `(inventario_id, reserva_id)` and `BoletoRepository::buscarPorInventario` ignores `anulado` tickets.

### Venues and inventory (Recintos / Inventario)

Venues are fixed (≤100 seats each), seeded by `RecintoSeeder` (Teatro Soirée: numbered Platea+Balcón; Auditorio Central: numbered VIP + `general` zone). The admin picks a venue when creating an event, sets a price per localidad, and publishing (`PublicarEventoUseCase`) calls `IGenerarInventarioEventoUseCase` in the same transaction: it requires a price on every localidad (422 `localidades_sin_precio`) and creates one `inventario` row per seat (numerada) or `capacidad` rows with null `asiento_id` (general); idempotent. `php artisan inventario:generar {evento}` backfills events published before this existed. `GET /api/eventos/{id}/disponibilidad` (public) returns zones with price, counts and seats. `POST /api/reservas` accepts `inventario_ids` (numbered seats) and/or `cupos: [{localidad_id, cantidad}]` (general zones, rows picked with `FOR UPDATE SKIP LOCKED` so concurrent buyers don't collide; SQLite ignores the lock clause), capped by `reservas.max_boletos_por_persona` (5) **per person per event** — paid + still-active holds + this request, counted inside the transaction after locking the user's `usuarios` row (`IReservaRepository::lugaresDePersonaEnEvento(..., bloquear: true)`) so two simultaneous requests from the same person can't both pass; over the limit → 422 `limite_por_persona` (`LimitePorPersonaException`); `GET /api/eventos/{id}/mi-cupo` → `{maximo, usados, disponibles, pagados, apartados, pendientes[{reserva_id, lugares, total, expira_en}]}` drives the seat map's "te quedan N" and the "apartados sin pagar" box (countdown + "Continuar con el pago" → `Auth.irAPagar` / "Liberar lugares" → `DELETE /api/reservas/{id}`), so a buyer who left the gateway can resume or release; events whose date already passed reject new reservas (422) and the client seat map shows "Evento finalizado" — and throttled 10/min per user. Seat map views: client `/eventos/{eventoId}/asientos` (select seats, running total, polls every 8 s, keeps the selection in sessionStorage across login via `/login?volver=`), admin `/admin/eventos/{eventoId}/asientos` (live occupancy every 4 s, header with only a "← Catálogo de eventos" back link to `/admin?seccion=catalogo` — `admin.js` opens `?seccion=` on load); shared renderer `public/js/asientos.js`.

### Catalog listing

`GET /api/eventos` (Catálogo, `ListarEventosUseCase` → `{eventos, total}`) returns every published/sold-out upcoming event when called without params (the admin seat view relies on that). With `?pagina=N[&por_pagina=M]` (default `catalogo.eventos_por_pagina` = 6, max 48) it paginates in the DB (`LIMIT/OFFSET`, ordered by `fecha_evento, id`) and adds `meta {pagina, por_pagina, total, hay_mas}`. The catalog page loads page 1 (its first 5 also feed the "Destacados" carousel) and "Ver más funciones" appends the next pages.

### My purchases (Mis compras)

`/mis-compras` (`resources/views/reservas/mis-compras.blade.php`, `public/js/mis-compras.js`, header/menu from `catalogo.css`/`catalogo.js`) lists the user's paid (`confirmada`) reservas from `GET /api/mis-compras` (`ListarMisComprasUseCase` → `{proximas, pasadas}`, both newest purchase first by `pagado_en`, each with evento, lugares, total, `pagado_en`, `referencia`; the page has a "Volver a la cartelera" link); `GET /api/reservas/{id}` returns one own reserva's evento + lugares (used by "¡Pago aprobado!"). Both 404 another user's data via `ReservaNoEncontradaException`. Each purchase links to `/mis-compras/{reservaId}/boletos` (`resources/views/reservas/boletos.blade.php`, `public/js/boletos.js`, `public/css/boletos.css`): one ticket per seat, built from `GET /api/reservas/{id}` — whose `lugares[]` now include `color` and `boleto {id, estado, usado_en}` (left join on `boletos`, read-only; the secret `codigo_qr` is never returned) — and the QR image from the Boletos module's `GET /api/boletos/{id}/qr` (fetched with the bearer token → blob `<img>`; only `emitido` tickets get one; a ticket that no longer works — show already held, `usado` or `anulado` — shows its QR greyed out (a decorative one when the API no longer serves it) with a label such as "Función finalizada" / "Utilizado"). The page polls ~1 min while the queue worker is still emitting, and has a print/PDF stylesheet. "¡Pago aprobado!" links straight to that purchase's tickets.

### Ticket scanning (QR → `/b`) and access control

The QR of a ticket encodes `<host>/b#<codigo>` (`GeneradorQrBoletoSvg::enlace`; host = `config('boletos.url_publica')` / `BOLETOS_URL_PUBLICA` — e.g. the ngrok URL to test with a phone — or else the request's host; the secret code goes in the fragment so it never reaches server logs). The page `/b` (`resources/views/boletos/entrada.blade.php`, `public/js/entrada-boleto.js`) removes the fragment from the address bar and asks `POST /api/boletos/consultar {codigo}` (`ConsultarBoletoEscaneadoUseCase`; accepts the bare code or the whole URL), whose answer depends on who scans: no session or any other client → `{vista: 'tienda'}` (redirect to the catalog, nothing about the ticket is revealed); the owner → `{vista: 'propietario', reserva_id, boleto_id}` → `/mis-compras/{reserva}/boletos#boleto-{id}` (`boletos.js` centers and highlights it); admin or operador → `{vista: 'personal', puede_entrar, motivo, es_hoy, boleto, evento, lugar}`, drawn by `public/js/verificacion-boleto.js` (+ `verificacion-boleto.css`): green "Puede entrar", amber "válido pero no es para hoy", red for used (shows when it entered)/annulled/cancelled/past. **Scanning never uses the ticket**: the staff taps "Registrar entrada", which calls Freyder's `POST /api/boletos/validar` (now admin **and** operador). Panel section "Control de acceso" (`public/js/admin-acceso.js`, admin + operador) scans continuously with the device camera (`BarcodeDetector`, or jsQR from jsDelivr loaded only when missing), pauses while a result is shown, keeps the last 8 scans, and has a field to paste the code; the browser camera needs https or localhost — over plain http on a LAN the phone's own camera app opening `/b` still works.

### Notifications (avisos)

Every notice is ONE row in `notificaciones` (Freyder's outbox, `guardarUnica` with an idempotency key) with `tipo`, `url`, `push_en` (`leida_en` is unused since the inbox was removed). There is **no inbox**: notices arrive as system notifications (Web Push) and by email, for all three roles. `EnviarNotificacionCorreoJob` sends the push first (once, `push_en`; failures are only reported to the log; the title gets an emoji per `tipo`) through `Domain/Abstractions/Notificaciones/IEnviadorPush` → `Infrastructure/Notificaciones/Push/EnviadorPushWeb` (`laravel-notification-channels/webpush`, VAPID keys in `.env` via `php artisan webpush:vapid` — the private key never goes to Git — subscriptions in `push_subscriptions`; `Usuario` needs both `HasPushSubscriptions` and `Notifiable`), then the email (`NotificacionCorreo`, with a "Ver en Soirée" button to `url`) for `canal = email`. Customer notices: `compra_confirmada`, `recordatorio`, `cambio_fecha`, `evento_cancelado`, `reembolso_procesado|rechazado`. Staff notices (`NotificarPersonalUseCase`, push + email): `reembolso_solicitado` and `devolucion_pendiente` (admins), `evento_casi_lleno` (≥ `notificaciones.umbral_casi_lleno`) / `evento_agotado` (admins + operators, from `ProcesarCompraConfirmadaJob`). API: `POST /api/push/suscribir|desuscribir` (only browser push services, as in tienda-ropa). Frontend: `public/js/notificaciones.js` (`window.Avisos.push`: estado/activar/desactivar/sincronizar on this device — `sincronizar` re-registers an existing subscription to whoever is logged in —, handles blocked permission, Brave and iPhone), `public/sw.js` (shows the push, opens its `url`), the bell `public/js/campana.js` + `campana.css`: a single button that turns push on/off on this device (filled = on, struck through = off/blocked) with a short note, no list and no counter — in the store it goes next to the account menu when `catalogo.js` fires `tienda:sesion` (included via `partials/avisos.blade.php`), in the panel it mounts on `[data-campana]` in the top bar (colors via `--campana-*` variables set in `admin-tema.css`). Push needs https (localhost and ngrok work), and the `queue` container must be restarted after changing notification code.

### Footer and privacy

Store pages (catalog, event detail, Mis compras, boletos, privacy) include `resources/views/partials/pie-pagina.blade.php` (styles in `catalogo.css`). `/privacidad` (`resources/views/legal/privacidad.blade.php`) explains what data is collected and why; it's linked from the footer and the registration form. Contact address: `config('marca.contacto')` (`MARCA_CONTACTO`). Keep the policy in sync when adding new personal data or third parties.

### Catalog banner

The catalog hero background is one image or one short video chosen in the admin panel (section "Banner", `public/js/admin-banner.js`): `GET|POST|DELETE /api/admin/banner` (multipart field `archivo`; jpg/png/webp/mp4/webm, ≤ `catalogo.banner.max_mb`; video length is only checked in the browser) and public `GET /api/catalogo/banner` (`data: null` → default theater photo). Single row in `banners`; `ActualizarBannerCatalogoUseCase` stores the file first, deletes it if the DB write fails, and only then deletes the previous file. Files go through `IAlmacenMultimedia` (`Infrastructure/Catalogo/AlmacenMultimediaLaravel`, same resize-to-WebP logic as the tienda-ropa project; videos stored as-is) on the `public` disk, so `php artisan storage:link` is required. The dark tone is pure CSS (`.portada-fondo__medio` in `catalogo.css`). Upload limits: `docker/php/subidas.ini` (copied in the Dockerfile) and `client_max_body_size` in `docker/nginx/default.conf`.

### Admin panel theme

`/admin` (Luis's `admin.css` + `admin.js`) is skinned by `public/css/admin-tema.css`, loaded after `admin.css`: appearance only (colors, fonts, borders), all rules scoped to `body.tema-soiree` and driven by `--t-*` variables. `html[data-tema="claro|oscuro"]` picks the palette (light by default); an inline script in the view's `<head>` applies the saved choice before paint and `public/js/admin-tema.js` wires the sun/moon button (`#btnTema`, `localStorage.tema_panel`). The sidebar stays dark in both themes. When styling new admin components, use the `--t-*` variables so both themes work. On ≤ 850 px the sidebar becomes an off-canvas menu: `.barra-movil` ("Menú" button `#btnMenu`, brand, current section name from `admin:recargar`) opens `#menu-lateral` with icons + labels over `#menuVelo`; it closes on picking a section, the ✕, the overlay or Esc (logic in `admin-tema.js`, styles at the end of `admin-tema.css`, overriding Luis's icon-only/horizontal rules in `admin.css`). The panel section "Catálogo de eventos" (`#catalogo-panel`, `public/js/admin-catalogo-eventos.js`, registered in `admin.js` like `banner`) shows event cards from `GET /api/admin/eventos/catalogo` (`AdminCatalogoEventosController` → `BuscarEventosAdminUseCase` → `Data/Admin/CatalogoEventosAdminRepository`; roles admin + organizador): every state, server-side filters `nombre`, `estado`, `recinto_id`, `desde`/`hasta` (event date), `pagina`/`por_pagina` (default `catalogo.admin_eventos_por_pagina` = 12), upcoming first, with `lugares`/`vendidos` occupancy per event. Each card carries the same action buttons as the old events table, built by `admin.js` (`window.AdminEventos.acciones(evento)` → `eventActionGroup`); "Editar"/"Precios" open their form in the Eventos section and closing it returns to the catalog. `admin.js` dispatches `admin:recargar` (`detail.section`) on every `load()`, which the catalog uses to refresh after publishing/editing. The Eventos section is now only for creating/editing: its table and filters are hidden by the theme and an `.eventos-aviso` links to the catalog. The "+ Nuevo evento" button lives in the hero (`.hero-acciones`, shown only while `#eventos-tools` is visible); `#eventos-tools` stays in the DOM (hidden by the theme) because `admin.js` and `admin-event-filters.js` rely on it.

### Audit log (Bitácora)

Separate database `eventos_bitacora` on the same MySQL server (connections `bitacora` — user with only SELECT/INSERT — and `bitacora_admin` — root, only for `bitacora:instalar`), migrations in `database/migrations/bitacora` (not run by plain `migrate`); triggers reject any UPDATE/DELETE, so rows are immutable. Rows are written by the `RegistrarBitacora` middleware (appended to the `api` and `web` groups) from the route table in `Infrastructure/Bitacora/CatalogoBitacora` (`"METHOD uri"` → categoria, accion, whitelisted `campos` — never passwords, codes or QR —, optional `antes` via `IContextoBitacora`, `describir`, `registrarFallos`); a 403 on `api/admin/*` is logged as `sesion.acceso_denegado`. Failures inside the log are swallowed (`rescue`) so they never break the user's request. **To audit a new action, add an entry to `CatalogoBitacora` and a test in `tests/Feature/Bitacora/BitacoraTest.php`.** Dates stored in UTC; `GET /api/admin/bitacora` (admin only, `BuscarEnBitacoraUseCase`) filters by categoria, resultado, rol (`sin_sesion` = no user), usuario (name/email) and Guatemala-day `desde`/`hasta`. Panel section "Bitácora" (`public/js/admin-bitacora.js`). Tests: `BITACORA_HABILITADA=false` in `phpunit.xml`; `BitacoraTest` enables it and migrates its own SQLite in-memory connection. Missing install → 503 `bitacora_no_disponible`.

### Admin dashboard (section `resumen`, labelled "Dashboard") and reports

`GET /api/admin/resumen` (`ObtenerResumenAdminUseCase`): `totales.operadores` (rol organizador), `pagos_aprobados`, `monto_pagos_aprobados` (only `aprobado` payments — pending/rejected are not income); `reservas_por_estado` / `eventos_por_estado` always list every state in logical order (`{estado, etiqueta, total}`, zeros included; `activa` = currently held within the TTL). Reports `GET /api/admin/reportes/{excel|pdf}?tipo=eventos|reservas|pagos|usuarios[&desde&hasta]` (admin only): `Data/Admin/ReporteAdminRepository` → `GenerarReporteAdminUseCase` (indicadores, desglose por estado/rol, full detail rows; dates converted UTC → `config('reportes.zona_horaria')`, filter days are Guatemala days; over `reportes.limite_excel|limite_pdf` → 422 `reporte_demasiado_grande`) → drawn by `Infrastructure/Admin/ReporteExcel` (single sheet: header, KPI cards, breakdown, detail with autofilter) or `resources/views/admin/reportes/pdf.blade.php` (DomPDF: tables only, no flex/grid).

### Event form (panel → Eventos)

The Eventos section has no list and no "+ Nuevo evento" button: the CREATE form is always open (`closeEventForm()` reopens it while in Eventos, so the draft survives section changes; "Cancelar" becomes "Limpiar formulario" with a confirm modal). "Editar" from the catalog opens the same form in edit mode (`aperturasFormulario` makes the latest `openEventForm` win) and returns to the catalog. Editing a draft also saves its prices (`PUT .../precios`, only allowed while `borrador`; published events show them read-only). Saving shows a success modal (`admin:evento-guardado` → `dialogo()` in `admin-evento-formulario.js`). Field order: name + date, phrase, description (≤ 600 chars, shown in full on the event detail page and catalog card; the experience shows the first 170) (with counters), venue + plan, photos, costs, prices.

`public/js/admin-evento-formulario.js` adds four helpers on top of Luis's form in `admin.js`, coordinated by the events `admin:formulario-evento` (`{eventoId|null}`, dispatched at the end of `openEventForm`) and `admin:evento-guardado` (`{creado}`):
- **Photos** (3, required): picked/dropped files are uploaded at once to `POST /api/admin/eventos/imagenes` (`SubirImagenEventoUseCase` → `IAlmacenMultimedia`, WebP ≤ 1920 px, `catalogo.imagen_evento_max_mb`) and their URL goes into the hidden inputs `imagen_url`, `imagen_url_2`, `imagen_url_3` that `admin.js` already sends. Validation `App\Rules\ImagenDeEvento` accepts `/storage/eventos/...` or (old events) an HTTPS URL. Photo 1 = catalog card + first scene of the event experience; 2 and 3 = the other two scenes (`eventos/experiencia.blade.php` replaces the `landing.paradas` images with `evento.imagenes` from the disponibilidad payload). Unused uploads are deleted daily by `eventos:limpiar-imagenes` (files older than one day not referenced by any event).
- **Venue plan**: "Ver plano del recinto" → `GET /api/admin/eventos/recintos/{id}/plano` (`ConsultarPlanoRecintoUseCase`, same shape as disponibilidad with every seat free) drawn by `MapaAsientos` (`asientos.js`/`asientos.css` are loaded in the admin view), showing the typed or suggested price per zone.
- **Costs** (`admin-costos.js`): one field per category; recinto and artistas are required (> Q0) on create and on every costs save (`GuardarCostosEventoDTO::exigirBasicos`).
- **Suggested prices**: from total costs, desired margin and expected occupancy (sliders) — gross income = costs ÷ (1 − commission − margin), split by zone weight (VIP 1.6, platea/palco 1.25, balcón/general 1.0, other numbered 1.15), rounded up to Q5 — plus a projection (income, profit, break-even seats).
- **Phrase**: optional `eventos.frase_destacada` (≤ 70 chars — column is 90 —, with a live counter) titles the FIRST scene of the event experience, whose text becomes the start of the description (`Str::limit` 170); if empty the event name is used. Scenes 2 and 3 keep the generic purchase copy from `config('landing.paradas')`. The experience header has a "← Cartelera" link (`.cabecera__volver` in `landing.css`).
- **Draft memory**: a NEW event's fields (including uploaded photo URLs, costs, prices and sliders) are kept in `localStorage.soiree_borrador_evento` and restored on reopening until saved or "Descartar borrador".

### Event date and rescheduling

`fecha_evento` is typed in Guatemala time and stored in UTC (`App\Rules\FechaDeFuncion::aUtc`, applied in `GuardarEventoRequest::validated()`; the form fills the `datetime-local` input converting back with `dateForInput`). `FechaDeFuncion` requires a future date no further than `catalogo.max_meses_evento` (3) months ahead. A **published** event can be rescheduled from its edit form (`PATCH /api/admin/eventos/{id}/contenido` with optional `fecha_evento`, admin only), but only postponed — never earlier than its current date — after a confirm modal; if the minute changes, `NotificarCambioEventoUseCase::notificarCambioFecha` queues one email per buyer (paid reservas) with the old and new date in Guatemala time, and the response carries `fecha_cambiada` / `compradores_avisados`.

### Finances (Finanzas)

Soirée produces its own events, so profit = ingresos netos (approved payments − approved/processed refunds − gateway commission `finanzas.comision_pasarela`, 3.5 % of everything charged, since the gateway does not return it on refunds) − production costs. Refunds count on the day they are approved: the sales chart draws charged amounts above the axis and refunds below it (`ventas[].monto|reembolsos|neto|boletos|devueltos`), and `totales.ventas` / `boletos` are net (`ventas_brutas`, `reembolsos`, `boletos_vendidos`, `boletos_devueltos` = tickets annulled in the period); margin = profit ÷ (charged − refunded). The dashboard card "Ingresos netos" = approved payments − `monto_reembolsado`. Costs live in `costos_evento` (categoria `CategoriaCosto`, concepto, monto; soft deletes keep history). Admin **and operador** register them: in the event form (`admin-costos.js` → `payload.costos` on create, validated with `CostoEventoController::reglas()` and saved in the same transaction as the event; on edit `PUT /api/admin/eventos/{id}/costos` replaces the list, only if it changed) and `GET` the same URL lists them. **Only the admin sees profits**: `GET /api/admin/finanzas?desde&hasta` (Guatemala days, ≤ 1 year, default last `finanzas.dias_ventas` days; `ObtenerFinanzasUseCase`): sales grouped by day (≤ 45 days), ISO week (≤ 210) or month, compared with the previous period of the same length; `historial` = events *closed* (held or cancelled) whose date falls in the period, with their final `ganancia|perdida` — they feed the totals (ganancia, margen); `proximos` = not closed yet, with `en_venta|cubierto|sin_costos` and `equilibrio_boletos` = costs ÷ average ticket price net of commission. Rendered in Resumen by `admin-finanzas.js`: one period filter row (presets 7/30/90 days / this year + custom range) scoping everything, two SVG column charts side by side (sales; profit per closed event, losses below the baseline) with tooltips, and a tabbed table (historial / próximos, 8 rows + "Ver más"); colors `--t-serie-ingresos`, `--t-ganancia|perdida` in `admin-tema.css` were validated with the dataviz palette validator against `--t-panel` in both themes — re-validate if you change them.

### Data model notes

- Domain users live in the `usuarios` table (entity `Domain/Entities/Auth/Usuario`); the default Laravel `users` table/`App\Models\User` is leftover scaffolding.
- Business tables carry audit columns (`created_by`/`updated_by` → `usuarios`, timestamps, soft deletes).
- Seat-hold flow: `inventario` rows (per event/localidad/asiento) are locked with `estado` + `bloqueado_hasta` and linked to a `reservas` row with `expira_en` (TTL). The `scheduler` container runs `schedule:run` every minute to sweep expired reservations/holds, and the `queue` container (`queue:work redis --tries=3`) handles seat TTL, payment retries and emails. Both have `(estado, <timestamp>)` indexes for that sweep.
- Circular FK `inventario.reserva_id` is added in the `reservas` migration — keep migration order in mind when adding cross-module FKs.
